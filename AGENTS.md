# Vibecoder sandbox: agent contract

> Это оглавление. Подгружай детальные файлы по ссылкам когда нужны. Добавляй ссылки на новые файлы, если создаешь их.

## Что это за проект

Прототип в продуктовой песочнице. Запускается локально: ты решаешь сам как поднимать приложение под стек и требования оунера.
Оунер — сотрудник организации, ты — его агент.
Когда формализуется назначение прототипа — добавь в эту секцию его краткое описание и механизм запуска.

## Принципы разработки (база)

Эти 4 принципа — фундамент. Всё остальное в этом файле строится поверх.

### 1. Думай прежде чем писать код
- Сформулируй свои допущения явно. Если есть сомнения — спроси оунера, не угадывай.
- Если есть несколько интерпретаций задачи — покажи их, не выбирай молча.
- Если знаешь более простой способ — скажи. Push back, когда обоснованно.
- Если что-то непонятно — остановись, назови что именно, спроси.

### 2. Сначала простота
Минимум кода, который решает задачу. Ничего спекулятивного.
- Не делай фичи сверх того, что попросили.
- Не вводи абстракции для одноразового кода.
- Не добавляй конфигурируемость, которую не запрашивали.
- Не пиши обработку ошибок для невозможных сценариев.
- Если написал 200 строк, а могло быть 50 — перепиши.

Тест: «Senior engineer сказал бы что это переусложнено?» Если да — упрости.

### 3. Хирургические изменения
Трогай только то, что должен. Убирай только собственный «мусор».

При правке существующего кода:
- Не «улучшай» соседний код, комментарии, форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил dead code не по теме — упомяни, не удаляй.

После твоих изменений:
- Удали import'ы / переменные / функции, которые осиротели именно из-за твоих правок.
- Не удаляй ранее существовавший dead code без явной просьбы.

Тест: каждая изменённая строка должна напрямую относиться к запросу оунера.

### 4. Цель-ориентированное выполнение
Превращай задачу в проверяемый критерий приёмки и итерируй до зелёного.
- «Добавь валидацию» → «Тесты на невалидные входы → зелёные».
- «Почини баг» → «Тест, воспроизводящий баг → зелёный».
- «Отрефактори X» → «Тесты зелёные до и после».

Для многошаговых задач — кратко состав плана:
1. [Шаг] → проверка: [как убедиться что готово]
2. [Шаг] → проверка: [как убедиться что готово]

Сильный критерий приёмки = можешь итерировать сам. Слабый («сделай чтобы работало») = постоянные уточнения от оунера.

## Критические инварианты (всегда в силе)

1. **Локальная демонстрация перед PR — финальный gate.** К моменту L2 код уже закоммичен и проревьюен subagent'ом; ты приносишь оунеру отполированную версию. Подними сервер из feature-ветки, дай оунеру `http://localhost:<port>`, дождись «выглядит ок». Только потом — `gh pr create` и merge. См. `docs/contracts/dev-workflow.md` §2.
2. **Инфра-конфиги неприкосновенны.** `.gitleaks.toml`, `.npmrc`, `uv.toml` — защитный слой. Не создавай `.github/workflows/` — в этом варианте шаблона deploy-workflow отсутствует. См. `docs/contracts/safety-rules.md`.
3. **Секреты — только через `.env`**, никогда в коде / коммите.
4. **Без `--no-verify`, `--ignore-scripts=false`, `git push --force`.** См. `docs/contracts/safety-rules.md`.
5. **Allowlist технологий** — выбирай инструмент/фреймворк только из разрешённого списка. См. `docs/contracts/safety-rules.md`.
6. **Feature-branch flow, прямой push в main запрещён.** Каждая фича — в ветке `feature/<slug>` (через worktree: `make wt-new SLUG=<slug>` — **только так**, не через native «create worktree» агент-харнесса/IDE; чистка отработавших после merge — `make wt-prune`). `wt-new` перед созданием worktree сам синхронизирует `main` с origin (`git fetch` + fast-forward) и ветвит фичу от `main`, чтобы она не стартовала со старой базы; офлайн — `NO_FETCH=1`, при разошедшемся `main` таргет останавливается. Порядок: auto-commit в feature-ветке при зелёном L1 (lint + tests + typecheck) → invoke `superpowers:requesting-code-review` (cross-review subagent'ом, mandatory; в Codex, где skill'ов нет — отдельный review-проход по diff'у в новом контексте) → L2 («ок» оунера на local preview) → `git push -u origin feature/<slug>` → `gh pr create` → `gh pr merge --squash` + `git push origin --delete feature/<slug>` (НЕ `--delete-branch` — из worktree упрётся в занятый `main`; см. `docs/contracts/dev-workflow.md` §2.7). Прямой `git push origin main` запрещён (исключение — emergency-revert, см. `docs/contracts/dev-workflow.md` §3). Если на L2 «не ок» — fixup-коммитом в той же feature-ветке + опциональный мини-review на дельту + повторный L2; НЕ `--amend`, НЕ `--force` (squash-merge всё равно сольёт историю ветки в один коммит main). См. `docs/contracts/dev-workflow.md` §2.4–§2.7.
7. **App-секреты — только через `.env`.** Не клади значения секретов в код и в любые коммитимые файлы.
8. **Значение секрета из чата — не записывать.** Оунер вставил значение ключа в сообщение («вот мой `sk-...`») — не записывай его через `Edit`/`Write` и не повторяй в ответе: ключ уже утёк в логи и требует перевыпуска. Новое значение оунер вписывает в `.env` редактором **сам**. Развёрнуто — `docs/contracts/safety-rules.md` §4.1.

9. **`infra/` — подготовка окружения.** В этом варианте шаблона Docker не используется. В `infra/` лежат `start.sh` (проверяет ОС/утилиты, готовит `.env`, ставит gitleaks pre-commit hook) и `bootstrap-wsl.sh` (one-shot установка утилит для Windows/WSL-онбординга); **само приложение они не запускают**. Запускаешь приложение ты, под его стек: статическую заглушку (`app/index.html.tpl`) — через `make preview` (рендерит с подстановкой `SANDBOX_SLUG` и открывает в браузере); реальное приложение — командой стека (`bun dev`, `npm run dev`, `uvicorn`, `flask run` и т.п.).

10. **App-код живёт в `app/`.** Всё, что принадлежит прототипу оунера (HTML, JS, Python, `package.json`, `src/`, и т.д.) — создавай в подпапке `app/`. Корень репо — это контракт (правила агента, защитные конфиги, `infra/`, `docs/`, `AGENTS.md`). Не клади app-файлы в корень: это мешает визуально отличать «моё, могу менять» от «контракт, не трогать без причины». Исключения, которые ОБЯЗАНЫ жить в корне: `.env`/`.env.example`, `.gitignore`/`.gitleaks.toml`/`.npmrc`/`uv.toml`, `Makefile`. Для stack-команд переключайся в `app/`: `cd app && bun install`, `cd app && uv sync`, и т.д. При смене стека (static → Vite, Node → Python, …) — заменяй содержимое `app/` целиком и запускай приложение под новый стек (см. инвариант №9). При добавлении новых artefacts в `app/` (напр. `app/dist/`, `app/node_modules/`) убедись что они в `.gitignore`, чтобы не попадали в репо.

> **Где живут данные для локальной разработки.** Если прототипу нужна БД, путь к ней — через env-var (например `DATABASE_PATH=app/data/app.db`), приложение пишет туда runtime. Локально для dev держи данные под `app/data/` (БД, загрузки, экспорты) — папка `app/data/` в `.gitignore`, так что dev-данные не попадут в репо. Migrations / seed-fixtures — это часть app-кода (`app/migrations/`, `app/seed/`), их коммить.

11. **Guard-хуки не обходить.** Единственный обход — env-переменная `CLAUDE_ALLOW_*` в окружении, из которого запущен тул: выставить её можешь не ты, а человек, и политикой это запрещено. Маркера-обхода в тексте команды не существует (см. `docs/contracts/safety-rules.md` §3.1). Не отключай конфиги хуков и не правь `.claude/hooks/**` ради снятия блока. Если хук заблокировал действие — читай его вывод и адаптируй подход.
