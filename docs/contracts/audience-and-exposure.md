# Audience and exposure

Контракт: какой класс call surface ты делаешь — определяет, какие защиты обязательны и какие решения должен принять оунер до первого коммита фичи.

> Это не альтернатива `./safety-rules.md` (там про секреты, git, supply-chain — всегда в силе). Это — вторая ось: **кто будет дёргать твой пилот наружу, и что из этого следует**.

## 1. Зачем этот контракт

Vibecoder по дефолту подразумевает «прототип для оунера и команды». На практике пилоты бывают разные:

- Внутренний инструмент команды (10 человек знают URL).
- Read-only публичный сервис (например, MCP-обёртка над публичным API маркетплейса).
- Полноценный публичный продукт с записью данных и многопользовательской авторизацией.

Эти три класса требуют **разных** защит, и без явного выбора класса агент либо недозащищает (public без rate-limit → ваш сервер становится бесплатным multiplier'ом нагрузки на upstream), либо переусложняет (внутренний инструмент команды с обвесом, который никому не нужен).

Этот контракт фиксирует три tier'а exposure (**T1 / T2 / T3**), обязательные защиты для каждого, и pre-flight чек-лист, который агент проходит с оунером **до начала кода**.

## 2. Когда запускать чек-лист

**Запускай перед началом любой фичи, которая создаёт новую call surface наружу.** Конкретно:

- Новый HTTP-эндпоинт кроме `/healthz` (любой `GET /...`, `POST /...`).
- Новый MCP tool / новый MCP-сервер.
- Webhook receiver (callback от внешнего сервиса).
- Публичная HTML-форма / форма обратной связи.
- File upload endpoint.

**Не нужно** запускать на:

- Чисто внутренние правки (рефакторинг кода без новых endpoint'ов).
- Изменения существующего UI без нового call surface.
- Заливку контента (правки текстов, картинок на существующих страницах).
- Hello-world заглушку из онбординга (она T1 by default — placeholder, не реальная фича).

**Тир привязан к фиче, не к проекту.** В одном пилоте можно иметь T1-админку (только для оунера) и T2-публичный API (для всех читателей) — это нормально. На каждую новую фичу — отдельный проход чек-листа.

## 3. Уровни exposure

### 3.1 T1 — Internal (default)

**Кто пользуется:** оунер + ≤ ~10 человек его команды. URL передаётся приватной коммуникацией (Пачка, личное сообщение). Не публикуется нигде.

**Auth:**
- Допустимо без auth (полагаемся на «никто не знает URL»).
- Допустимо с одним общим bearer-токеном, который оунер раздаёт вручную.

**Нагрузка:** пренебрежимая (десятки запросов в день, не больше).

**Обязательные защиты:** **никаких сверх дефолтных.** `/healthz` необязателен (в локальном варианте его никто не опрашивает); если добавляешь — он не влияет на exposure-тир. Никакого rate-limit, кэша, hard-pagination — не нужно для 10 человек.

**Примеры:** внутренний дашборд команды; страница «статус проекта» для коллег; форма заявок от сотрудников; админка прототипа.

### 3.2 T2 — Public read-only

**Кто пользуется:** произвольные внешние пользователи. URL может быть в публичном каталоге, в соц.сетях, в посте.

**Сущностное ограничение:** **только чтение** и **только публичные данные** (которые и так доступны всем — каталог маркетплейса, открытые госданные, публичный контент оунера). Никакой записи на сторону, никакого user-specific состояния.

**Auth:**
- Допустимо без auth (анонимный публичный endpoint).
- Допустимо «user приносит свой ключ к upstream» (если данные приходят со стороннего сервиса).

**Нагрузка:** непредсказуемая. Один популярный AI-агент может сгенерить 100 параллельных запросов в одной reasoning-итерации.

**Обязательные защиты:**

1. **Rate-limit per IP.** Без него сервер становится multiplier нагрузки на upstream / тратит ресурсы CI без контроля. Default-точка отсчёта: **60 req/min/IP** (агент уточняет под конкретный кейс). Реализация:
   - FastAPI: `slowapi` или ручной in-memory bucket.
   - Hono: `hono-rate-limiter`.
2. **TTL-кэш для upstream-вызовов** (если данные не должны быть real-time). Не каждый одинаковый запрос должен лететь в upstream. TTL обсуждаешь с оунером — для справочных данных 60-300 секунд нормально; для inventory/наличия — нужен real-time. Реализация:
   - Python: `cachetools.TTLCache`.
   - Node: `lru-cache` с TTL.
3. **Hard limit на пагинационные параметры.** Если есть параметры `limit` / `page_size` / `count` — фиксируй верхний потолок (`max_limit=50` или похожее). Без этого один запрос `limit=10000` может слить весь upstream-каталог за раз.
4. **Документированный набор tools/endpoints с явными descriptions.** Для MCP — конкретные tool descriptions, которые LLM-клиенты используют для выбора. Для REST — OpenAPI или README с примерами. Без этого «публичный сервис» сводится к набору непонятных URL'ов, которыми никто не воспользуется правильно.

**Recommended-но-не-обязательно:**

- Логирование request rate (для оунера — видеть, что вообще происходит).
- UTM / X-Source header в upstream-вызовах (если оунер хочет attribution).

**Примеры:** MCP-сервер с публичным каталогом flowwow; публичная страница «найти доставку в моём городе» с поиском по открытому API; обёртка над открытым датасетом.

### 3.3 T3 — Public с write / OAuth / per-user state

**Кто пользуется:** произвольные внешние пользователи, **и хотя бы одно из:**

- Фича пишет данные (создаёт заявки, отправляет сообщения, проводит платежи).
- Фича хранит per-user состояние (личный кабинет, история, корзина).
- Auth требует OAuth user-flow (Google / Microsoft / GitHub login).

**Текущий sandbox не предназначен для T3.** Это не «запрещено», но это означает:

- Шаблонных решений для multi-tenant дизайна (per-user storage, identity, изоляция данных) нет.
- OAuth-callback контур (refresh tokens persistence, multi-tenant token storage) не покрыт.
- Reliability ожиданий публики (no downtime при перезапуске, high availability) local-запуск не обеспечивает: один процесс, рестарт = downtime в секунды.
- Юридическая сторона (ToS upstream-сервиса, GDPR/152-ФЗ для персональных данных пользователей) — на оунере, не на шаблоне.

**Что делать при T3-запросе:**

1. Проговори вслух с оунером всё перечисленное выше. Не молча принимай задачу. Общайся простым и понятным языком.
2. Спроси, готов ли оунер взять на себя архитектурный дизайн multi-tenant'а и юридическую часть.
3. Если ответ «да» — продолжай, **но в PR body честно зафиксируй**: `Audience: T3 — outside sandbox template defaults. Owner explicitly accepts: <что именно>`.
4. Если ответ «не знаю» / «помогите придумать» — эскалация в #itsupport / к ответственному за платформу. Это не работа агента в одну сессию.

**Примеры:** многопользовательский сервис с регистрацией; платная подписка; бот с OAuth к Google Calendar для всех; форма приёма платежей.

## 4. Pre-flight чек-лист

Запускаешь в формате диалога с оунером **до первого коммита фичи**. Делаешь это сам, без напоминания от оунера — это часть pre-work (см. `./dev-workflow.md` §2.1).

**Вопрос 1: Кто будет дёргать этот endpoint / tool / форму?**
- «Только я и команда» / «приватная ссылка» → T1.
- «Любой человек из интернета» → перейти к Вопросу 2.
- «Не знаю» → помоги классифицировать: «Ты будешь публиковать URL где-то открыто (соц.сети, каталог, пост)? Или только пересылать приватно?»

**Вопрос 2 (если не T1): Эта фича пишет данные или меняет внешний мир?**
- Только читает → T2 кандидат, перейти к Вопросу 3.
- Пишет (создаёт, обновляет, отправляет, оплачивает) → **T3**, см. §3.3.
- Хранит per-user состояние (личный кабинет, история) → **T3**, см. §3.3.

**Вопрос 3 (если T2-кандидат): Откуда данные? Какой upstream?**
- Свой API (flowwow / внутренний) → ок, T2 подтверждён.
- Сторонний API, ключ серверный (общий для всех пользователей) → **проговори риск**: квота сгорит публикой, лимит upstream-сервиса заблокирует ключ, оплата на оунере. Если оунер ок — T2 с обязательным мониторингом квоты.
- Сторонний API, **user приносит свой ключ** → ок, но это уже не «без auth» — выбери T2-вариант с заголовком/параметром для user-key.
- Несколько upstream → классифицируй каждый отдельно по этому же вопросу.

**Вопрос 4 (если T2 со сторонним upstream): ToS upstream разрешает re-host публично?**
- Свой API → N/A.
- Сторонний — оунер уточняет в ToS. Если не уверен — пометь как **T3-эскалацию** (юридический риск > технический).

**Вопрос 5: Какой конкретно набор tools / endpoints / форм?**
- Список конкретных операций. Это уже product-decision, не technical: фиксируется в PR body.

### После прохождения чек-листа

1. **Зафиксируй tier в PR body** первого PR этой фичи в формате:
   ```
   Audience: T2 — public read-only.
   Upstream: <upstream API name> (свой / сторонний).
   ToS: <verified / N/A / TBD by owner>.
   Operations: <список tools/endpoints>.
   ```
   Это аудит-trail: следующая сессия / следующий агент / следующий ревьюер видит, на что подписывался оунер.

2. **Включи обязательные защиты для тира** (§3.1 / §3.2 / §3.3).

3. **При сомнении эскалируй**: скажи оунеру «не уверен, что текущий sandbox это покрывает», и предложи переформулировать в более низкий тир (например, T3 → T2 если убрать write-операции).

## 5. Что НЕ покрывает этот контракт

- **Discovery** (как «все» узнают про твой публичный endpoint) — задача оунера: каталог MCP-серверов, упоминание в документации flowwow для разработчиков, маркетинг. Шаблон тут не помогает.
- **Per-pilot observability** (логи / метрики / дашборды видимые оунеру) — выходит за scope текущего sandbox; будет адресовано отдельным аспектом инициативы.
- **Cost-control / billing tracking** для upstream-квоты — оунер сам решает, как мониторит.
- **Anti-abuse beyond rate-limit** (DDoS, ботнеты, credential stuffing) — fail2ban на уровне Sandbox-сервера ловит 401-штормы, но не сложные атаки. Для T2 это **достаточно** в дефолтных ожиданиях прототипа; если кейс требует промышленной защиты — эскалация.
