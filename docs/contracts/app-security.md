# App security (build-time)

Превентивные правила безопасности app-кода. Применяй **по ходу написания**, не после. Это слой, ортогональный остальным контрактам:

- `./safety-rules.md` — секреты, git, supply-chain, allowlist (всегда в силе).
- `./audience-and-exposure.md` — кто дёргает наружу (T1/T2/T3) и обязательные защиты публичных surface (rate-limit, CORS, кэш, hard-pagination).
- **этот файл** — как не написать уязвимость в самом коде.

Cross-review субагент (инвариант №6 в `AGENTS.md`) проверяет эти правила перед PR — но первичная защита в том, чтобы не писать нарушение изначально.

## Threat-model пилота

Дефолт — внутренний инструмент (T1): закрытый контур (посторонние снаружи не достучатся), shared-secret auth, SQLite, исходящие вебхуки. Правила ниже стреляют именно в этом контуре. Расширенные кейсы (OAuth/SSO user-flow, multi-tenant изоляция данных, публичный write) — это T3, вне дефолтов шаблона (см. `./audience-and-exposure.md` §3.3); их безопасность проектируется отдельно с оунером.

## Принципы (3 рамки)

1. **Доверие к источнику.** Всё, что пришло извне процесса (тело HTTP-запроса, query/path/headers, ответ внешнего API, содержимое загруженного файла, пользовательский env) — **недоверенное**, пока не прошло явную валидацию. Доверенное — только то, что прослеживается до константы в коде или провалидированной схемы.
2. **Fail closed.** Ошибка валидации, истёкший токен, недоступная зависимость → **отказ в доступе**, не «пропустим на всякий случай».
3. **Глубина защиты.** Проверка на фронте не отменяет проверку на бэке. Каждый слой защищается независимо.

## 1. Ввод и эндпоинты

### 1.1 Валидация входов
Body / query / path / headers — по строгой схеме: типы, форматы, диапазоны, allow-list значений. Неизвестные поля отклоняй.
- Делай: Zod / valibot (Node), Pydantic (FastAPI), явная схема (Flask / Hono).
- Не делай: `req.body.x` прямо в логику или БД; type coercion строки в число без проверки; «валидация» только на длину.

### 1.2 Авторизация (owner-check)
Если у фичи есть роли (`admin` / `editor` / `viewer`, см. `./safety-rules.md` §1.2.1) или per-user данные — после аутентификации проверяй **право на конкретный ресурс**. `id` из запроса не подтверждает право на него.
- Делай: достал объект по `id` → сверь владельца / роль с текущей сессией.
- Не делай: роль из тела запроса или из подменяемого клиентом поля; одна проверка на «весь админский» роутер без гранулярности.
- Красный флаг: смена `id` в запросе даёт доступ к чужому ресурсу (IDOR).

### 1.3 Mass assignment
Сущность не создаётся и не обновляется напрямую из тела запроса — только через явный allow-list полей.
- Не делай: `Object.assign(model, req.body)`, `Model.update(req.body)`, `...req.body` в конструктор сущности.
- Красный флаг: клиент может выставить поле, которое не должен (`isAdmin`, `role`, `balance`, `ownerId`).

### 1.4 Утечки в ошибках
Ответ об ошибке не содержит стектрейса, пути ФС, текста SQL, версий. На login / сбросе пароля не различай «нет пользователя» и «неверный пароль» — это энумерация аккаунтов.
- Не делай: `err.stack` / `err.message` в HTTP-ответ; debug-режим в проде.

## 2. Данные (SQLite)

### 2.1 SQL injection
Запросы — **только параметризованные** (placeholder'ы `?` / `:name`). Никакой конкатенации или интерполяции ввода в текст запроса.
- Делай: `db.prepare('SELECT * FROM t WHERE id = ?').get(id)`; `cur.execute('... WHERE id = ?', (id,))`.
- Не делай: f-string / template literal / `+` с пользовательским вводом в SQL.
- Красный флаг: ввод влияет на структуру запроса, а не только на данные.

### 2.2 Path traversal
Пути к файлам (загрузки и экспорт, см. `./safety-rules.md` §1.2.3) не строй из недоверенного имени без нормализации и проверки границы.
- Делай: сгенерируй имя сам (uuid) или проверь, что `realpath` результата внутри разрешённой папки.
- Не делай: склейка пути с пользовательским именем; доверие к `../`, абсолютным путям, null-байтам. `path.join` сам по себе не защищает.

### 2.3 Over-fetching
Не отдавай наружу больше, чем нужно. Hash пароля, токены, внутренние поля не покидают слой данных.
- Не делай: `SELECT *` с последующей сериализацией всей строки в ответ; ORM-сущность в API без проекции / DTO.

### 2.4 Небезопасная десериализация
Недоверенные данные не скармливай механизмам, способным исполнить код или создать произвольный объект.
- Не делай: `pickle.loads`, `yaml.load` без `SafeLoader`, `!!python/object`.
- Делай: JSON + валидация схемой (см. §1.1); `yaml.safe_load`.

### 2.5 Персистентность
Данные, которые должны пережить перезапуск или пересоздание процесса (БД, загрузки, экспорты, кэш, сессии), пишутся только в **предназначенное окружением durable-хранилище** — не в эфемерный (`/tmp`) и не в read-only путь. Где именно это хранилище — задаёт контракт окружения проекта (в деплой-варианте — персистентный том; в локальном — отведённая папка данных проекта). Неуместный путь → данные молча теряются при пересоздании, либо процесс падает на записи (read-only ФС).
- Делай: путь к данным — из явной конфигурации (env-var), указывающей на durable-хранилище окружения; подкаталоги под ним создавай в runtime.
- Не делай: писать в `/tmp` или иной эфемерный / read-only путь то, что должно сохраниться; «случайный» путь, не прослеживаемый до durable-хранилища окружения.
- Красный флаг: путь к БД / загрузкам не прослеживается до durable-хранилища, заданного контрактом окружения.

## 3. Внешние вызовы

### 3.1 Command injection
Внешние команды — формой с **массивом аргументов без shell**, не строкой с интерполяцией ввода.
- Делай: `execFile('convert', [inPath, outPath])`; `subprocess.run([...], shell=False)`.
- Не делай: `exec(\`... ${userInput}\`)`, `os.system(f'...')`, `shell=True` со строкой, содержащей ввод.

### 3.2 TLS verification
Проверка сертификатов **включена** на всех исходящих соединениях.
- Не делай: `verify=False` (httpx / requests), `rejectUnauthorized: false` (Node).

### 3.3 SSRF
Если фича делает исходящий запрос по URL **из пользовательского ввода** — это уже не дефолтный кейс. Egress-политику см. в `./safety-rules.md`, секция «Sensitive operations» (новый хост без секрета и без упоминания оунером — спроси). Когда URL приходит от пользователя: allow-list хостов и блокировка приватных диапазонов (`127.0.0.0/8`, `10/8`, `169.254.169.254` — metadata) над **итоговым** IP после резолва.

## 4. Фронтенд

### 4.1 XSS
Недоверенные данные не попадают в DOM как разметка или код.
- Не делай: `innerHTML` / `v-html` / `{@html}` / `dangerouslySetInnerHTML` с пользовательским вводом; `javascript:`-URL; `eval` / `new Function` / `setTimeout(строка)`.
- Делай: текст через `textContent` / `{{ }}` (Vue экранирует по умолчанию); если нужен HTML из недоверенного источника — санитизируй (DOMPurify).

### 4.2 Секреты в клиентском бандле
В коде фронта и собранном бандле нет серверных секретов, приватных ключей, внутренних URL.
- Красный флаг: `VITE_*` / `import.meta.env.*` с приватным значением — всё с этим префиксом попадает в браузер. Серверные ключи остаются на сервере (через `.env`, см. `./safety-rules.md` §4).
- Не делай: сторонний API-ключ с серверными правами в JS-коде; закомментированные креды.

### 4.3 Хранение токена сессии
Сессия — в cookie с `httpOnly` + `Secure` + `SameSite`, не в `localStorage` / `sessionStorage` и не в URL.
- Почему: `localStorage` доступен любому XSS-скрипту; токен в URL утекает в историю браузера, Referer, логи.

### 4.4 Утечки через клиентский код
В `console.log` нет токенов и PII. Стектрейсы и детали ошибок не показываются пользователю в UI.

### 4.5 Open redirect
Переход по пользовательскому значению (`window.location`, `router.push`, параметр `?next=` / `?return=`) — только после проверки: цель внутри своего домена, протокол из allow-list (отсекай `javascript:`).

## 5. Криптография

Перекликается с `./safety-rules.md` §1.2.1 («не катай свою крипту»):
- Пароли — адаптивный хеш (**bcrypt / argon2 / scrypt**), никогда MD5 / SHA1 / plaintext.
- Сравнение секретов и токенов — **constant-time** (`crypto.timingSafeEqual`, `hmac.compare_digest`), не `==`.
- Случайность для токенов и id сессий — криптостойкая (`crypto.randomBytes`, `secrets.token_*`), не `Math.random` / `random`.

---

**Что НЕ здесь** (осознанно вне дефолтного threat-model): Kubernetes / Terraform / IaC, OAuth-SSO user-flow, multi-tenant изоляция данных, DNS rebinding, cache poisoning, ReDoS, postMessage / SRI / clickjacking. Если кейс реально это требует — это T3 либо эскалация (см. `./audience-and-exposure.md`).
